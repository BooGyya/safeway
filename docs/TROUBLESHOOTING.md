# SafeWay 트러블슈팅 통합 기록

교통약자 맞춤 안전 경로 추천 서비스 (팀 소보로빵 · 대전 2반 2팀)
Django REST Framework + Vue 3 / 2026.05 ~ 2026.06

> 개발 대화 기록과 커밋 로그 기반 정리본을 통합한 문서입니다.
> 커밋 해시가 있는 항목은 실제 커밋으로 확인된 건이고, 없는 항목은 대화 기록에서 복원한 건입니다.

---

## A. 환경 · 초기 세팅

### A-1. ImageField 마이그레이션 실패
- **증상**: `makemigrations` 시 `accounts.User.profile_image: (fields.E210) Cannot use ImageField because Pillow is not installed.`
- **원인**: 커스텀 유저 모델에 `ImageField` 사용, Pillow 미설치
- **해결**: `pip install Pillow` → 통과. 이후 `pip freeze > requirements.txt`로 반영

### A-2. .env 값 따옴표 혼입
- **증상**: API 키를 못 읽는 것으로 의심되는 상황 반복
- **점검**: `print(repr(os.getenv('KAKAO_REST_API_KEY')))`로 숨은 문자 확인
- **해결**: `KEY="값"` / `KEY='값'` → `KEY=값`으로 통일
- **함정**: `repr()` 출력의 작은따옴표는 파이썬 표기일 뿐, 실제 값의 따옴표가 아님 (이걸 오인해서 한동안 헤맴)

## B. 인증 · 계정

### B-1. 카카오 로그인 KOE010 (가장 오래 걸린 이슈)

**증상**
```json
{
  "error": "토큰 발급 실패",
  "detail": {
    "error": "invalid_client",
    "error_description": "Bad client credentials",
    "error_code": "KOE010"
  }
}
```
인가 코드는 콜백에 정상 도착하는데 토큰 발급 단계에서만 400.

**디버깅 과정**

| # | 가설 | 조치 | 결과 |
|---|------|------|------|
| 1 | 원인이 안 보임 | 응답에 `detail: token_json` 추가 | KOE010 확인 → 진단 시작점 확보 |
| 2 | settings에 키 없음 | `KAKAO_REST_API_KEY`, `KAKAO_JS_KEY` 추가 | 로그인 화면 진입까지 성공 |
| 3 | .env 로드 실패 | `os.getenv()` 출력, 32자 확인 | 정상 |
| 4 | 따옴표/공백 | `repr()` 확인 후 제거 | 원인 아님 |
| 5 | 리다이렉트 URI 불일치 | 콘솔 등록값 대조 (끝 슬래시 포함) | 정상 |
| 6 | 인가 코드 만료 | 시크릿 창에서 재시도 (인가 코드는 1회용·단명) | 원인 아님 |
| 7 | 동의항목 미설정 | 닉네임·프로필 사진 선택 동의로 변경 | 원인 아님 |
| 8 | 비즈 앱 / 테스트 앱 | 콘솔 확인 | 해당 없음 |
| 9 | **앱 혼동** | 기존 앱(workfree) 키를 쓰고 있었음 → SafeWay 키로 교체 | 부분 원인 (동의 화면에 "workfree"로 뜨던 게 단서) |
| 10 | 요청 페이로드 확인 | `token_data`, `token_json` print | client_id·code 정상인데 여전히 실패 |
| 11 | **클라이언트 시크릿** | 카카오 보안 알림으로 발견 — 시크릿 활성화 상태인데 토큰 요청에 미전송 | **진짜 원인** |

**해결**: 플랫폼 키 → REST API 키 → 클라이언트 시크릿 → 카카오 로그인 항목 **비활성화**
(대안: 시크릿을 `.env`에 넣고 토큰 요청 body에 `client_secret` 포함)
→ 200 OK, 유저 생성 + JWT 발급 + `created: true` 확인

**배운 점**: 외부 API 에러는 응답 body를 그대로 노출시키는 게 첫 단추였고, 제공사 콘솔/메일 알림이 가장 정확한 진단이었음

### B-2. redirect_uri 하드코딩 (`3ab357e`)
- `http://127.0.0.1:8000/...`가 코드에 박혀 있어 환경 전환 불가 → `KAKAO_REDIRECT_URI` 환경변수로 분리

### B-3. 로그인 시 이전 계정으로 자동 로그인 (`d8f264f`)
- **원인**: 카카오 세션이 남아 계정 선택 없이 바로 진입
- **해결**: 인증 URL에 `prompt=login` 추가해 매번 로그인 화면 노출

### B-4. 카카오 신규 가입자 별명 처리
- 신규 가입자가 별명 없이 서비스 진입 → 콜백 리다이렉트 URL에 `needs_nickname=true/false` 파라미터를 붙여 프론트가 별명 입력 페이지로 분기
- 마이페이지에서 별명 빈값·공백만 입력이 통과되던 문제 → `strip()` 검사 후 400 반환

### B-5. 비밀번호 변경 실패 (`d729f9e`)
- **원인**: 백엔드가 `new_password2` 확인 필드를 요구하는데 프론트가 미전송
- **해결**: 요청에 `new_password2` 추가


**부수 이슈**
- API Key IP 제한 → 개발 단계에선 `0.0.0.0/0`
- 발신번호 사전 등록·인증 필요
- SOS 문구가 `username` 기반이라 어색 → `user.nickname or user.username` fallback (`9e7aea9`)
- 위치는 위경도를 받아 구글 지도 링크로 첨부

## C. 공공데이터 수집

### C-1. 장애인편의시설 — 일일 호출 한도 초과
- **증상**: 99,000건 수집 중 429 (Too Many Requests)
- **해결**: 자정 리셋 후 **100페이지부터 이어받기**로 스크립트 수정 → 최종 181,901건
- **부가**: `items`가 1건일 때 list가 아닌 dict로 오는 케이스 분기, 페이지 실패 시 3회 재시도

### C-2. 승강기 API — 전체 조회가 0건
```xml
<response><header><resultCode>00</resultCode><resultMsg>NORMAL SERVICE.</resultMsg></header>
<body><items /></body></response>
```
- **원인**: `BuldElevatorService`는 승강기 번호·건물 단위 **상세 조회용**. 조건 없는 전체 목록 조회 미지원 (`totalCount` 태그조차 없음)
- **시도**: 엔드포인트 교체(`openapi.elevator.go.kr`) → 서버 자체 접속 불가(서비스 종료 추정)
- **해결**: API 포기 → CSV 기반 import로 전환, 서울+대전 38,614건 적재
- **재정비**: 정확도가 떨어져 **지하철역 엘리베이터 CSV**(서울 552건, 대전 37건)로 교체. 좌표가 `POINT(경도 위도)` WKT라 정규식 파싱, cp949 인코딩, 노드 ID로 중복 방지

### C-3. 엘리베이터 조회가 항상 빈 배열
- **원인**: CSV 적재 데이터에 위경도가 없는데 조회는 위경도 range 필터
- **1차**: 카카오 실시간 장소 검색으로 대체 → **"엘리베이터" 키워드 검색이 엘리베이터 제조 회사를 반환**하는 문제 발생
- **최종**: 지하철역 엘리베이터 DB 기반으로 회귀

### C-4. 저상버스 데이터 확보 실패 (기능 보류)
- 서울 T-Data `v2xVehicleInformation` → `responseCode: 410`
- 공공데이터포털 → `Key인증실패: SERVICE KEY IS NOT REGISTERED ERROR.[인증모듈 에러코드(30)]` (승인 대기)
- 조사 결과 **전국 저상버스 위경도 데이터 자체가 부재** → 기능 스킵

### C-5. facility_type이 전부 'other'
- **증상**: 편의시설 181,901건 전부 `other`, 경사로/점자블록 필터링 불가
- **조사**: API 응답을 직접 덤프해보니 `wfcltDivCd`는 **건물 유형 코드**(017=주차장 등)이고, 편의시설 종류 세분화 필드가 애초에 없음
- **결론**: 세분화 불가 → `other` 유지, 엘리베이터만 별도 데이터셋으로 분리 대응

### C-6. 서울 음향신호기가 0건으로 조회됨
- **진단**: 서울 신호등 1,239건은 있는데 `has_audio=True`가 0건
- **원인 1**: 수집 스크립트의 음향신호기(`sondSgngnrYn`) 파싱 오류 → 재수집
- **원인 2**: 공공데이터 `opratnYn`이 **전 데이터 'N'** 이라 `is_operating` 필터가 전부 걸러냄 → 필터 제거 (`fca48bb`)

### C-7. 이동지원센터 sido 필드 오염
- **증상**: 서울 조회 0건. 집계해보니 `충청남도 금산군`, `의왕도시공사` 같은 값이 `sido`에 통째로 저장
- **해결**: sido/sigungu 분리 파싱 후 재적재(176건). 수집 중 `ConnectionResetError(10054)`는 재시도 로직으로 자동 복구

### C-8. 신호등 road_nm 하드코딩
- **증상**: 서울 신호등 `road_nm`이 전부 `'서울'`이라 안내 문구가 무의미
- **해결**: 서울시 교차로 데이터(`A008_P.shp`)의 `CSS_NAM`과 위경도 최근접 매칭 → `시청`, `강남역` 등 실제 교차로명 저장
- **결과**: 신호등 44,020건 / 음향신호기 16,270건 / 잔여시간표시기 11,818건

## D. 실시간 보행신호 (서울 V2X) — 기술적으로 가장 깊은 파트

### D-0. 구조적 난제 — itstId 매핑
- V2X 신호제어기 API는 **`itstId`(교차로 ID) 기반**이라 위경도로 직접 조회 불가
- 경로상 횡단보도 좌표 → 최근접 교차로 매핑이 선행되어야 함 → **2,779개 교차로 매핑 테이블 구축**
- 8방향(북/동/남/서 + 대각) 보행신호 중 실제 진행 방향에 해당하는 값을 계산하는 로직 필요

### D-1. 잔여시간이 339초처럼 비정상 표시 (`4e3345a`)
- **원인 2가지**
  1. 해당 방향이 보행 녹색이 아닐 때 API가 `36001`이라는 **"값 없음" 센티넬**을 반환하는데, 이를 실제 값처럼 표시
  2. **단위 오해** — 문서상 센티초처럼 보였으나 실제는 **데시초(1/10초)**
- **해결**: 센티넬 필터 + `÷100` → `÷10` 정정

```python
UNKNOWN_VALUE = 36001  # 해당 방향이 보행 녹색이 아닐 때의 "값 없음" 센티넬
if value and value < UNKNOWN_VALUE:
    result[direction] = round(float(value) / 10, 1)  # 데시초(1/10초)
```

### D-2. 신호값이 5→4→3→2→1→5→4… 반복 (`b87b82d`)
- **원인**: 해당 방향 보행신호가 없을 때(차량신호 구간) **다른 방향 값 중 최솟값으로 fallback**하는 코드가 있어 남의 카운트다운을 빌려옴
- **해결**: fallback 제거 → `None` 반환하고 "대기 중(차량 신호)"로 표시. `v2x_available` 플래그를 따로 둬서 **"V2X 미설치"와 "현재 차량신호"를 구분**

### D-3. 상세 패널이 전부 "0초 남음"으로 굳음 (`97b7a68`)
- **원인**: 경로 검색 시점의 스냅샷이 그대로 남음
- **해결**: 좌표 기준 재조회 엔드포인트 `/api/routes/realtime-signal/` 신설, 패널 열 때(`watch(showRouteDetail)`) 재조회

### D-4. 0초에서 멈추고 갱신 안 됨 (`a1f4506`)
- **해결**: 1초 틱마다 0초 도달 항목 자동 재조회 + 중복 호출 방지 가드(`refreshingSignalIds`)

### D-5. 처음부터 "대기 중"인 신호는 영원히 갱신 안 됨 (`a698094`)
- **원인**: 최초부터 null인 항목은 "0초 도달 시 재조회" 조건에 걸리지 않음
- **해결**: null 항목도 주기적으로 재조회

### D-6. 1일 1,000회 API 한도 소진 (`abae3a0`)
- **트레이드오프**: 간격이 길면(60초) 짧은 보행신호를 놓치고, 짧으면 한도 소진
- **해결**: null 항목 재조회 간격을 **15초**로 확정 (정확도 우선)

### D-7. 함께 붙인 실시간 소스
서울 실시간 인구밀도(`citydata_ppltn`), 카카오맵 교통정보 레이어, OpenWeatherMap

## E. 경로 탐색 & 안전점수

### E-1. 계단 회피 경로가 실제로 동작하지 않음
- **증상**: `user_type=normal`과 `wheelchair` 결과가 완전히 동일
- **원인**: TMAP **보행자 경로 API는 `optionRouteType`을 지원하지 않음** (자동차 경로 전용) — 파라미터가 무시됨
- **경위**: 검증 없이 "지원한다"고 안내해서 잘못된 구현이 들어갔고, 되짚어 확인하면서 발견
- **대응**: 국내 지도 API 중 보행자 계단 회피를 공식 지원하는 곳이 없음을 확인 → 다중 경로 탐색(추천/계단회피/큰길우선/날씨추천) 구조로 전환, 휠체어 사용자에겐 주변 엘리베이터·경사로 정보를 함께 제공

### E-2. 보행속도가 소요시간에 반영 안 됨 (`a3b83a0`) — 2중 원인
- **1차**: 백엔드가 요청 body를 무시하고 DB의 `walk_speed`(기본 1.0)만 사용 → `request.data.get('walk_speed', ...)` 우선 적용
- **2차**: 프론트가 값을 보내는데도 동일. **TMAP이 `speed`를 무시하고 자체 계산**하는 것이 원인
```python
if transport_type == 'walk' and distance > 0 and user_speed > 0:
    duration = int(distance / user_speed)
```
- **교훈**: 프론트/백엔드 책임을 payload로 먼저 가르고, 외부 API가 파라미터를 실제로 반영하는지 별도 검증

### E-3. 안전점수가 장거리 경로에서 항상 0점 (`dcf7a4f`)
- **경위**: 공식을 두 번 갈아엎음
  1. 초기 — 음향신호기·잔여시간표시기 **비율** 기반 (계산만 하고 경로 선택에 영향 없음)
  2. 개편 — **거리 · 횡단보도 · 관리자 확인 위험구간** 기반 감점 방식
  3. 재수정 — 감점이 상한 없이 무한 누적되어 긴 경로는 무조건 0점
- **최종**: 항목별 감점 상한 도입 (**횡단 -0.35 / 거리 -0.25 / 위험구간 -0.45**)
- 택시는 안전점수가 무의미해 숨김, 도보 카드에만 노출

### E-4. 경로 주변 시설이 경로와 무관하게 반환
- **원인**: 전체 waypoint의 min/max로 만든 **bounding box + padding 0.005** 기반. 경로가 길면 박스가 거대해짐
- **해결**: waypoint를 20개 간격 샘플링 + 각 지점 반경 100~300m 이내만 수집, 중복 제거(seen set)와 개수 상한 적용

### E-5. 경로 주변 신호등 조회 기준 변경 (`491452d`, `fca48bb`)
- 음향신호기 기준 → **잔여시간표시기(`has_remndr`)** 기준으로 변경, 검색 반경 확대 (0.002 → 0.005)
- `is_operating` 필터 제거 (C-6과 동일 원인)
> 참고: 대화 기록에는 "`has_remndr=True` 필터를 제거하고 전부 반환" 논의도 남아 있습니다. 최종 코드가 어느 쪽인지는 커밋 순서를 한 번 확인해두면 좋아요.

### E-6. 안전도 점수 N+1 쿼리
- waypoint마다 DB를 조회(50개면 50회) → 쿼리 통합·샘플링으로 최적화

### E-7. 경로 탐색 실패 시 무응답 (`30a462a`)
- **증상**: 외부 API 실패 시 `waypoints=[], distance=0`을 그대로 반환 → 길이 없는 건지 오류인지 알 수 없음
- **해결**: `route_error` 도입, 실패 시 `400`과 명확한 메시지 반환 ("대중교통 경로를 찾을 수 없습니다." 등)

### E-8. 히스토리 중복 저장
- **1차 수정**: 동일 출발지+목적지+수단이면 `used_at`만 갱신
- **1차 수정의 버그**: `existing`이 있어도 `Route`는 무조건 `create`되어 테이블이 계속 불어남 + `existing` 분기에서 `route` 미정의로 `NameError`
- **최종**: `existing.route`를 직렬화해 반환, Route 생성은 신규일 때만. walk / bus·taxi 양쪽 적용. `order_by('-used_at')`

### E-9. 출발지/목적지 검색 레이스 컨디션 + 디바운스 (`4c39437`, `a22a6e1`)
- **증상**: 빠르게 입력하면 늦게 도착한 응답이 최신 결과를 덮어씀
- **해결**: 응답 도착 시 현재 입력값과 비교해 오래된 결과 폐기 + 디바운스

### E-10. 기타
- `Route` 모델에 `transport_type` 부재 → 히스토리에서 수단 식별 불가 → 필드 추가
- 카카오 자동차 경로의 `summary.fare.taxi` / `fare.toll` 미사용 → 택시 예상 요금 표시 추가
- 지하철·버스 구간 폴리라인 미표시 버그 수정, 노선명·승하차역·소요시간 단계별 안내 추가
- "추천 = 가장 빠른 경로"라는 잘못된 문구 수정, 실제 최단 경로에 배지 부여
- 동료의 "경로 추천 수정" 커밋과 충돌 → `build_route` 구조와 새 안전점수 공식을 **둘 다 살려서** 수동 병합

## K. 발표 활용 제안

**대표 사례: D. 실시간 보행신호 (V2X)**
문제 6개가 하나의 스토리로 이어지고, 원인이 전부 다릅니다 — 외부 API 스펙 오해(센티넬·단위) → 잘못된 fallback 설계 → 스냅샷 vs 실시간 → 갱신 트리거 누락 → 엣지 케이스 → 자원 한도 트레이드오프. "왜 어려웠나"를 설명하기 가장 좋은 소재예요.

**보조 사례 2개**
- **보행속도 미반영(E-2)** — 원인이 2중이라 "고쳤는데도 안 됐다"는 흐름이 살아 있고, 외부 API를 맹신하면 안 된다는 교훈이 명확합니다.
- **카카오 KOE010(B-1)** — 11단계 가설 검증 표 자체가 디버깅 태도를 보여주는 자료가 됩니다.
